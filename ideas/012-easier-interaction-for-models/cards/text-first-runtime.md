# Card 001 — Text-first runtime tier (your card)

## Story

You split Mayon into two tiers: a data-model + execution-runtime tier, and the web-UI on top of it. The next time you ask an agent for "user background in the system prompt," it works entirely against tier one — schema, prompt assembly, persistence — reading and writing plain text, and proves the feature there before any UI exists. The web-UI work then shrinks to mounting a textarea bound to an already-verified runtime, and Playwright stops being the place where features are proven.

## Playthrough (2026-10-31)

- **How it goes**: Week one is boundary-drawing, not code — everything data-and-decisions moves behind the runtime boundary, pixels-and-timing stay in the web tier. Mayon's existing seams (repos behind `getDb()`, `StorageDriver`/`RemotePgDriver`, `/api/db/query`, pglite test rig) are tier one already standing; what isn't standing is logic like prompt assembly, woven into front-end stores, which must be hauled down over weeks of extraction surgery. Once the tier exists, the "user background" feature is implemented and verified entirely as text — settings field at the repo layer, prompt slot in runtime prompt assembly, pglite tests proving both — and the UI work shrinks to mounting a bound textarea with a short browser smoke.
- **Snags**: (1) The boundary fight never ends — streaming rendering, expound offsets, and selection mapping are DOM-married, so every feature that straddles tiers relitigates where it lives; the split gives the debate a conference room, not a verdict. (2) A text-first runtime tier wants a client — a CLI or API surface plus an auth story for local agent use — which is a second frontend with a monthly bill. (3) Migration tax: weeks of regression-risk refactor of working prompt/orchestration code with no user-visible win until it lands.
- **Trade-offs**: Two contracts to keep honest instead of one; a deliberately dumber UI tier whose brains are now a hop away; the guarantee depends on ongoing discipline — one shortcut feature that bypasses the tier quietly rots it.
- **Delivers the what?**: Fully — browser automation stops being the bottleneck by construction, not convention. Strongest version of the goal in the deck, and the slowest to start paying.
- **Difficulty vs payoff**: difficulty L · payoff H · time-to-first-value ~4–6 weeks.
- **Your take**: "honestly, I don't know what to think of it — imagine I'm an LLM: how would I check that the prompt constructor returns the correct construct without the web-ui? or do we already have this in place?" — Code check (2026-10-31, see research.md): **already in place**. `assembleContext` (`src/lib/chat/context.ts`) builds the chat context against `repos`, verified non-browser by `context.test.ts` (pglite, text-in/text-out); quiz/lab `assemblePrompt` is pure over `repos.settings`. This softens the migration-tax snag — the prompt constructor never needed extracting. Card 001's remaining delta is the text client/boundary, not the logic. Follow-up: user reversed the question — "will an LLM find it hard to test this software?" — and floated an optional API-key-gated test tier using LLM-as-judge for prompt quality/guardrails. Answer (recorded in research.md): three of four test axes are already covered non-browser (bytes via context/assembly tests; model behavior via the mock-llm fixture system; pixels stay Playwright's); semantic quality judgment is the one uncovered rung — the judge idea targets exactly that gap. Kept on record as surfaced direction material for the verdict; no card carries it. Follow-up: user scoped prompt-quality eval out of the deck — deployed Langfuse for the prompt-engineering/eval workflow, decoupled from app code; "how good is the prompt" is another tool's job. 012's focus re-anchored on feature implementation/verification (decisions.md scope note); judge idea exits as a Mayon-codebase concern. User then asked the agent directly: "is there a win in doing the text-based layer first with a clear boundary vs. the UI (implementation besides the point, probably REST)?" — Agent's testimony: yes to the boundary, modest on the API. In-repo, the existing vitest+pglite harness beats a standing REST service for implementation-time verification (deterministic, offline, seeds state via repos in one function). The live stack already has coarse text doors (`/api/db/query`, `/api/health`) for RC-time checks. A formal REST layer earns its keep mainly for a long-lived external client driving Mayon feature-semantically. The bigger agent-side win is discipline: new feature logic landing behind the boundary with tests — which is what the unplayed cards argue about. ### Revised take (2026-10-31 — replayed after research.md findings, Langfuse scope-out, agent testimony)

- **How it goes (updated)**: Day one you declare the split; the audit then finds tier one mostly standing (repos, `StorageDriver`, `/api/db/query`, pglite harness, `context.test.ts`, mock-LLM rig). Week one becomes declaration + freeze, not extraction surgery; week two walks the residual straggler logic behind the seam, and the first feature ("user background") rides the tier in days — settings key + prompt slot + a repo-seeded test asserting the assembled string. The card's remaining fork is the client: build the REST surface (the original telling's bills: second frontend, contract drift, auth) or skip it — at which point the card dissolves into "keep the boundary honest," a rule rather than an architecture.
- **Snags (updated)**: boundary fights over DOM-married logic persist (streaming render, expound alignment); discipline decay — one shortcut feature rots the guarantee; identity snag — the visible win ratifies the present more than it builds the future.
- **Delivers the what? (updated)**: fully — and partly already banked; the bottleneck moved when the harness was built, not when the diagram gets drawn.
- **Difficulty vs payoff (updated)**: boundary-freeze scope — difficulty M · payoff H (partly banked) · time-to-first-value days–1 week. Full card including a REST/MCP client — difficulty L · the client is the L.
- **Pre-pick Q&A**: User asked whether, under this card, an LLM can "review" interactions from text alone. Answer: in three layers — interaction _consequences_ (state/data/flow) fully text-reviewable and already proven so (`chat.svelte.test.ts` simulates user actions store-level and asserts outcomes as text); interaction _semantics_ partially (jsdom component tests assert structure/roles/labels); _pixels_ (spacing, animation feel, streaming smoothness) never from text alone — handled by browser-as-camera (screenshot + vision review, precedent: ideas/007 rc-image-gate). The text-reviewable fraction equals the fraction of interaction logic behind the boundary — which is what this card (or the hybrid) grows.
