# Phase 1 Data Model: Security Posture Detection

**Feature**: `019-security-posture-detection` | **Date**: 2026-09-03

No application data is introduced — the app database, schema, and repositories are untouched. All three entities below are **platform-held records**: the feature creates/observes them through repo configuration and pipeline steps, never through app code.

## Entity: Security Finding

A detected weakness surfaced to the maintainer. One logical finding may be materialized in more than one platform surface (alert, code-scanning entry, workflow summary).

| Field | Type | Source of truth | Notes |
|-------|------|-----------------|-------|
| id | identifier | platform (alert ID / SARIF fingerprint) | stable across re-reports |
| kind | enum | derived | `vulnerable-dependency` · `artifact-vulnerability` · `blocked-credential` |
| severity | enum | platform/advisory | e.g. low / moderate / high / critical |
| target | reference | platform | dependency + affected range, or image + package, or pushed-content descriptor |
| fix_available | boolean | advisory | drives presence of an update proposal |
| status | enum | platform + human | `open` · `fixed` (auto on remediation) · `dismissed` (human) |
| discovered_at | timestamp | platform | when the advisory/block first fired |

**Validation rules** (from FRs): severity and target are always present (FR-002); `blocked-credential` findings never persist remotely (FR-005).

**State transitions**: `open → fixed` automatically when the affected dependency/artifact no longer matches the advisory (no manual cleanup — Edge Case 6); `open → dismissed` only by the maintainer.

## Entity: Release Assessment Record

A per-release posture snapshot covering exactly the two shipped artifacts. Materialized as: job-summary sections on the release's workflow run + SARIF uploads (one category per image) + JSON run artifacts. There is **no** new durable app-side storage.

| Field | Type | Source of truth | Notes |
|-------|------|-----------------|-------|
| release | tag reference | workflow trigger | the `vX.Y.Z(-rcN)` tag |
| artifact_results | list[2] | pipeline steps | exactly: `web-image`, `server-image` (D7) |
| artifact_results[].result | enum | scan step outcome | `clean` (explicit) · `findings` · `scan-failed` (FR-010 gap) |
| artifact_results[].findings | list[Security Finding ref] | SARIF/JSON | empty only when result is `clean` |
| produced_at | timestamp | run | when the scan leg finished |

**Validation rules**: every published release MUST yield a record (FR-007); `scan-failed` MUST be represented explicitly, never as silence (FR-010); the union MUST cover both artifacts (FR-007, D7).

**State transitions**: none after creation — records are immutable per release; each release produces a new one.

## Entity: Dependency Update Proposal

A prepared, reviewable change for one dependency, generated by the platform from open findings.

| Field | Type | Source of truth | Notes |
|-------|------|-----------------|-------|
| proposal | PR reference | platform | the Dependabot security-update PR |
| dependency | manifest path + package name | PR diff | e.g. `server/package.json` → `<pkg>` |
| from_version / to_version | semver pair | PR diff | fix-targeting per FR-003 |
| linked_findings | list[Security Finding ref] | alert linkage | advisory IDs in the PR body |
| status | enum | platform + human | `open` · `merged` · `closed` · `conflicted` (manual resolution) |

**Validation rules**: PR diff MUST touch only dependency sections of package manifests — never `version` fields, `CHANGELOG.md`, or other release bookkeeping (FR-004, D5; verified in quickstart). A `conflicted` proposal resolves only through ordinary human merge conflict resolution (FR-004).

**State transitions**: `open → merged` (maintainer merges) → linked findings transition to `fixed` on next evaluation; `open → closed`; `open → conflicted → (manual) → merged/closed`.

## Relationships

- One **Release Assessment Record** references 0..n **Security Findings** per artifact (2 artifacts exactly).
- One **Security Finding** of kind `vulnerable-dependency` MAY be addressed by 0..1 **Dependency Update Proposal** (0 when `fix_available = false`).
- Findings are independent of records: an alert can exist between releases; a record only snapshots what its release's scan observed.
